# Входные данные для проектирования ФОС

Документ фиксирует актуальные исходные условия, по которым собран фонд оценочных средств дисциплины. Детализация находится в [РПД](../docs/rpd.md), [индексе КИМ](../Modules/README.md), [условии проекта](../Project/README.md) и [модели измерения уровней КРМ](../methodical-guidelines/teachers-assessment/krm-level-model.md).

## ВХ-1 Наименование дисциплины

Б1.О.24. Java-разработка для систем искусственного интеллекта: ООП и обработка данных

## ВХ-2 Место дисциплины в учебном плане

### Семестр

Дисциплина осваивается на 2 курсе в 4 семестре.

### Объём дисциплины

Объём дисциплины составляет **3 з.е. / 108 часов**. В текущем комплекте материалов предусмотрены:

- вводный элемент 7.1 «Инженерная работа с ИИ-ассистентами и coding agents» — 2 академических часа;
- семь тематических модулей и 15 индивидуальных лабораторных работ;
- командный мини-проект №16 — 4 академических часа контактной работы и самостоятельная подготовка;
- самостоятельная работа, завершение проекта и подготовка к экзамену в пределах общего объёма дисциплины.

Точное распределение оставшихся часов по лекциям, лабораторным занятиям, самостоятельной работе и контролю определяется учебным планом конкретной реализации дисциплины. Репозиторий не устанавливает распределение, отсутствующее в [РПД](../docs/rpd.md#7-тематический-план).

### Пререквизиты

- переменные, типы, условия, циклы, функции и массивы;
- базовые алгоритмы и структуры данных;
- дискретная математика;
- основы реляционных БД, SQL DDL/DML, транзакций, ACID, индексов и нормализации.

## ВХ-3 Тематическое содержание проектной работы

Командный мини-проект №16 — [«Сервис обработки прайс-листов»](../Project/README.md). Команда из 2–3 человек разрабатывает серверное Java-приложение, которое получает грязные данные из нескольких источников, выполняет конкурентный ETL, сохраняет очищенный результат в PostgreSQL и предоставляет HTTP API.

### Обязательный технический результат — уровень Б

1. **Стек:** Java 17+, Maven или Gradle, Jackson, PostgreSQL через JDBC, `ExecutorService`, `JDK HttpServer`.
2. **Входные данные:** минимум три CSV/JSON-файла и не менее 1000 записей суммарно; фиксированный `seed`, межфайловые дубликаты и минимум пять классов ошибок.
3. **Extract:** параллельное чтение файлов с изоляцией ошибки одной записи от остальных корректных записей.
4. **Transform:** очистка, валидация, нормализация категории, валюты и даты, пересчёт цены в RUB по локальному справочнику, детерминированная дедупликация.
5. **Load:** PostgreSQL, `PreparedStatement`, UPSERT, таблицы `suppliers`, `offers`, `import_runs`, идемпотентный повторный импорт.
6. **Диагностика:** метрики `extracted`, `valid`, `rejected`, `duplicates`, `inserted`, `updated`, журналирование и DLQ без чувствительных данных.
7. **HTTP API:** `POST /imports`, `GET /imports/{id}`, `GET /offers`, `GET /health`; безопасные ответы `400`, `404` и `500`.
8. **Проверка:** два последовательных импорта, автоматические тесты, проверка метрик, ошибок, фильтров API и отсутствия новых логических дубликатов.
9. **Командная работа:** Kanban, feature branches, связь задач с изменениями, минимум один peer review на участника и объяснимый индивидуальный вклад.
10. **Воспроизводимость:** `README.md`, SQL-схема или миграции, конфигурация без секретов, `AGENTS.md`, данные, команды сборки, тестирования и запуска.

### Контролируемое применение ИИ

ИИ-агент разрешён для декомпозиции, генератора грязных данных, тест-плана, тестов, анализа ошибок, code review и не более одной ограниченной некритичной production-задачи на участника. Архитектуру, схему БД, правила ETL и идемпотентности утверждает команда. Сохраняются точные промпты, существенные ответы или diff, команды проверки, принятые и отклонённые предложения и окончательные исправления.

Агенту нельзя поручать проект целиком или одновременно генерировать Extract, Transform, Load и сервер. Пароли, токены, персональные данные и закрытые материалы агенту не передаются.

### Уровневая часть

Обязательная часть измеряет Б. По предварительному назначению преподавателя отдельные задания измеряют:

- С/П по PL-2.1 — Java Memory Model, высокая конкуренция, оптимизация GC и специализированное хранилище;
- С/П по PL-2.2 — Spark/MapReduce, Kafka/Flink, ClickHouse/Greenplum, профилирование и поддержка инфраструктуры ETL;
- П по LLM-5.2 — комплексный пайплайн с фактическим анализом attention, logits и выходов при наличии совместимого инструмента.

Уровни фиксируются накопительно и отдельно от процентной оценки по [рубрике проекта](../methodical-guidelines/teachers-assessment/project.md).

## ВХ-4 Профильные ИИ-роли КРМ

Основной ролевой профиль дисциплины и рекомендуемые уровни взяты из листа `Роли-компетенции наглядно` файла [КРМ v3.0](../data/krm-v3.0.xlsx).

| Профессиональная роль КРМ v3.0 | Компетенция и рекомендуемый уровень | Вклад дисциплины |
|---|---|---|
| Data Engineer (Инженер по данным) | PL-2 — С | обязательный Б и отдельные задания С/П по PL-2 |
| MLOps (Специалист по эксплуатации ИИ) | PL-2 — С; LLM-5 — Б | обязательный Б по PL-2 и LLM-5, отдельные задания С/П |
| TADS (Технический аналитик данных) | PL-2 — С | обязательный Б и отдельные задания С/П по PL-2 |

Дополнительное соответствие направления LLM-5:

| Профессиональная роль КРМ v3.0 | Компетенция и рекомендуемый уровень |
|---|---|
| AI Architect (Архитектор ИИ) | LLM-5 — Б |
| ML Engineer (Инженер МО) | LLM-5 — С |

Дисциплина оценивает индикаторы PL-2.1, PL-2.2, LLM-5.1 и LLM-5.2. Обязательная траектория подтверждает Б; отдельные задания С/П находятся в лабораторных №13–15 и проекте №16. Выполнение дисциплины формирует часть компетенций, но не означает присвоение профессиональной роли. Полные дескрипторы и связь «роль → компетенция → уровень» приведены в [§6 РПД](../docs/rpd.md#6-компетенции-и-профессиональный-ролевой-профиль-крм-v30).

## ВХ-5 Формы промежуточной аттестации

Формами промежуточной аттестации являются:

- [командный мини-проект №16](../Project/README.md) с отдельной [100-балльной рубрикой](../methodical-guidelines/teachers-assessment/project.md);
- [экзамен](../Exam/README.md): банк из 47 вопросов и проверяемый промпт-шаблон распределения вопросов по 25 билетам.

Готовый комплект билетов в репозитории не хранится: результат генерации должен быть проверен по правилам экзаменационного раздела до публикации.

Текущий контроль включает 15 индивидуальных лабораторных работ с отдельными рубриками. Процентная оценка показывает качество выполнения назначенной работы, а уровень КРМ — сложность подтверждённого результата по конкретному индикатору; они записываются раздельно по [единой модели Б/С/П](../methodical-guidelines/teachers-assessment/krm-level-model.md).

## ВХ-6 Индустриальные партнёры

В исходных данных программы указаны следующие индустриальные партнёры:

- ПАО «Сбербанк»;
- «АВАЛАБ»;
- ООО «СвязьРесурс-Кубань».

Текущие КИМ и мини-проект используют учебные предметные области и единый сценарий прайс-листов; репозиторий не заявляет, что задания согласованы или утверждены перечисленными организациями. Кейсы ниже сохранены как контекст для возможной адаптации дисциплины.

### Кейсы ПАО «Сбербанк»
1. Модель анализа инвестиционной привлекательности малого бизнеса
- Описание:
Банк активно развивает кредитование и инвестиционные инструменты для малого и среднего предпринимательства (МСП). Требуется создать модель, которая на основе открытых и банковских данных (выручка, расходы, тип деятельности, отзывы, онлайн-активность) оценивает инвестиционную привлекательность МСП.
- Цель:
Разработать систему рейтинговой оценки компаний малого бизнеса с возможностью визуализации факторов и динамики показателей.
- Ожидаемый результат:
Модель, присваивающая компании инвестиционный рейтинг (например, A–E), объясняющая ключевые параметры и дающая рекомендации для инвестора.

2. Индивидуальная оценка кредитоспособности клиента на основе поведенческих данных
- Описание:
Современный кредитный скоринг выходит за рамки финансовых данных. Необходимо исследовать, как поведенческие и цифровые следы (частота входа в мобильный банк, способы оплаты, география, время отклика) влияют на персональную оценку риска.
- Цель:
Разработать ML-модель, оценивающую вероятность дефолта по нестандартным поведенческим признакам (возможно — с explainable AI).
- Ожидаемый результат:
Прототип скоринговой модели, которая, помимо стандартных данных, учитывает цифровой профиль клиента и объясняет решения (SHAP, LIME и др.).

3. Анализ поведения пользователей в экосистеме цифрового рубля
- Описание:
Сбербанк участвует в пилотных проектах по внедрению цифрового рубля. Интерес представляет исследование пользовательских паттернов: как изменяются модели потребления, скорости операций, уровень доверия, сравнение с классическим безналом.
- Цель:
Построить модель анализа поведения клиентов, участвующих в транзакциях с цифровым рублем: частота, средний чек, контексты.
- Ожидаемый результат:
Отчёт и ML-модель, классифицирующая типы пользователей и выявляющая ключевые различия в предпочтениях и барьерах цифровой валюты.

### Кейсы от «АВАЛАБ»
1. Анализ обращений клиентов и CRM-переписки
- Описание:
В службе клиентского сервиса застройщика ежедневно обрабатываются десятки обращений (e-mail, звонки, мессенджеры). Требуется реализовать систему семантического анализа и классификации NLU: выявлять суть обращений, уровень удовлетворенности, отслеживать повторяющиеся запросы.
- Цель:
Автоматизировать первичный разбор и маршрутизацию запросов по тематике (сдача объекта, отделка, документы, жалоба и т.д.).
- Ожидаемый результат:
Прототип, который выделяет суть обращений и формирует дашборд по текущим «болям» клиентов.
2. Генерация рекламного контента для жилых комплексов
- Описание:
«АВА ГРУПП» регулярно запускает маркетинговые кампании для жилых комплексов. Необходимо исследовать использование диффузионных моделей для генерации изображений (визуализации интерьеров, окрестностей, видов из окон) и LLM — для описаний квартир, преимуществ района, инфраструктуры.
- Цель:
Создать инструменты для быстрой генерации продающих материалов без привлечения дизайнеров и копирайтеров на первых этапах.
- Ожидаемый результат:
Набор сгенерированных карточек объектов с текстом, изображением и логикой «живого» рекламного сообщения.
3. Генерация документации и шаблонов договоров
- Описание:
Юридический департамент регулярно работает с договорами долевого участия, актами приёма-передачи и другими документами. Использование LLM может значительно сократить время на подготовку черновиков — достаточно ввести параметры сделки.
- Цель:
Создать систему, которая генерирует адаптированные тексты документов по вводным данным (тип объекта, этаж, площадь, ФИО, сроки и пр.).
- Ожидаемый результат:
Генератор документов в формате Word или PDF с автоматической подстановкой параметров и соблюдением юридического стиля.

### Кейс от ООО «СвязьРесурс-Кубань»
- Описание:
Компания ООО "СвязьРесурс-Кубань" оказывает услуги связи. Работа с клиентами автоматизирована на базе CRM Битрикс 24. Для компании актуальны вопросы разработки первоначальных версий документов с помощью LLM и в перспективе автоматизации генерации большого количества документов по шаблонам с помощью LLM и RAG системы с интеграцией с Битрикс 24. Задачи включают в себя:
1. Разработка библиотеки промптов для генерации регламентов описания бизнес-процессов Битрикс 24.
2. Разработка библиотеки промптов для генерации техзаданий на основе параметров оказания услуг.
3. Разработка библиотеки промптов для генерации коммерческих предложений на основе параметров оказания услуг.
4. Разработка библиотеки промптов для генерации скриптов работы технической поддержки.
5. Разработка библиотеки промптов для генерации скриптов работы отдела продаж.
6. Апробация и сравнение различных языковых моделей для решения задач.
- Цель:
Автоматизировать работу сотрудников по составлению типовых документов.
- Ожидаемый результат:
Библиотека промптов и рекомендации по использованию LLM для решения поставленных задач.
